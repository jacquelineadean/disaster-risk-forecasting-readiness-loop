System designreport §5 · four planes, one contract

The agent proposes; the harness disposes.

Four planes, one contract per experiment series. Two invariants hold everywhere, and most of the design follows from them.

01 · Planes

Who may write what.

Report §5 asks for a deterministic scoring harness with zero LLM involvement: locked holdouts, Brier / BSS / reliability / AUC, an append-only experiment ledger — with the agent granted read access and no write access. The package layout is that sentence made into directories. The engine is the only place the agent's proposals land; the harness reads the contract and scores whatever it is handed; the ledger is the only thing the loop writes.

directoryplanerole
readiness/contracts.pythe contractschema, validation, digest and registry. Not edited while iterating.
readiness/config.pyharness policythe hazard catalogue, the record start year, the canary ceilings — the few things that apply to every contract.
readiness/connectors/data planebase (pinning, HTTP), Census counties, Storm Events, NWS zones, the read-only MCP server, and the Phase 1 feature sources — Gazetteer, Open-Meteo (ERA5), NRI, the pinned CLIMADA layer.
readiness/engine/the modelsclimatologies, persistence, the leaky oracle the canary exists to reject, and the Phase 1 candidates — logistic, gbm, an isotonic calibrator — plus features.py, the proposable feature-set catalogue.
readiness/agent/agent planethe orchestrator (both backends), the subagent definitions, and guard.py, the integrity guard around --backend claude.
readiness/harness/eval planemetrics, splits, labels, scoring, contract verdict, canary, ledger, and features.py — the feature channel and its temporal firewall. No LLM. No agent writes.
Import discipline
The engine may not import the contract module, the verdict or the canary: a model that can read its own acceptance criteria is a model that can be written to satisfy them. The harness does not import the engine or the agent: it must not depend on what it is judging.

02 · Invariants

Two rules, readable in one sitting each.

No model ever receives a holdout label.

TrainingView is the only channel a model gets data through, and it raises if handed a panel containing a validate or test year. predict() receives units and, for a Phase 1 model, the harness-built and audited feature rows for exactly those units, never a label. Labels are fetched in scoring._fit_predict() after predict() has returned — one function, in one file, which is the point.

# readiness/harness/scoring.py
view = TrainingView(train_panel, train_split)
model.fit(view)

request = PredictionRequest.from_panel(eval_panel, split)
probs = list(model.predict(request))

# Labels are fetched only now — after predict() has returned.
outcomes = list(eval_panel.labels)
# readiness/harness/splits.py
leaked = sorted(set(panel.years) - set(split.years))
if leaked:
    raise SplitViolation(
        f"TrainingView built over {split.name!r} but panel "
        f"contains out-of-split years {leaked}; refusing to "
        "expose holdout data")

Nothing in the harness calls a language model.

Verification has to be rules-based to be worth anything. If an LLM wants these numbers it reads them downstream, from the ledger. The verdict is mechanical: there is no judgement call, no "close enough", and no LLM in the path. If the numbers clear the contract's thresholds the model passes; otherwise it does not, and the failing checks say why.

The same discipline shapes the two loop backends. The local backend walks a fixed queue of candidates with no model calls at all — that is what CI runs and what the bit-for-bit criterion is checked against, because a loop whose control flow depends on a language model cannot have a bit-for-bit criterion. The claude backend runs the same loop with an Agent SDK orchestrator; every number on every card still comes from readiness.harness, and no subagent is granted a write tool.

The test-touch budget is persisted to disk, not held in memory — a budget that resets when you restart the process is not a budget — and the test split can only be scored through readiness promote, which requires an explicit --spend-test-touch flag and writes the test card in the same step.

03 · The contract

"Within an acceptable threshold" becomes a contract, not a feeling.

A contract is a JSON file in contracts/, written before any model is fitted. It is everything that defines one experiment series: the hazard and its Storm Events event types, the geography, the forecast period, what counts as a damaging event, what to do with zone-coded events, the locked splits, the test-touch budget, the reference model and the thresholds a model must clear.

The digest

Every field except the three labels is a criterion, and the criteria are hashed: the first sixteen hex digits of SHA-256 over their canonical JSON (keys sorted, no whitespace). The digest is stamped on every scorecard and every experiment card, and the verdict's contract provenance check fails for any card whose digest is not the current one. That is the whole enforcement mechanism for "pre-registered": nothing stops you editing a contract file, but every experiment run before the edit becomes visibly incomparable, and the ledger cannot be rewritten to hide it. Register a new name instead.

Validation is strict on purpose

A contract with overlapping splits, a split that starts before the record is trustworthy, a hazard nobody can look up, or a damage definition under which every event is "damaging" is refused at registration, not discovered in a ledger later. The sandbox shows the refusals verbatim.

The forecast unit
P(at least one damaging event of H in region R during period T). H is a named hazard mapped to Storm Events event types, R a US county in the scope, T a month, quarter or year.

Reference
Only climatology-pooled is implemented as a reference — the unsmoothed training base rate, issued everywhere. A contract must name it so the choice is explicit on the card.

04 · Data plane

Every source is fetched, checksummed and pinned before use.

layersourcerole
ground truthNOAA NCEI Storm Events, 1996–the validation target, every hazard: event type, county or zone, injuries, deaths, property damage
region universeCensus national county filethe panel denominator, any state or all — without it, counties that never had an event vanish and the base rate inflates
zone crosswalkNWS zone–county correlation filemaps a zone-coded event to every county in its forecast zone, under zone_policy: expand

Each Storm Events year file is national, so one download serves every state and every hazard: it is checksummed, split into one compact extract per state, and the raw bytes are discarded unless --keep-raw is set. snapshots/manifest.json is committed; the ~300 MB of raw pulls are not, so a clone reproduces the exact data version without carrying the bytes. A cached file with no manifest record counts as unpinned and is re-fetched rather than used. An experiment that cannot name its data version is not an experiment.

A contract's data version is a hash over exactly the pinned files its panel was built from — the county file, its years of Storm Events, and the crosswalk if it expands zones — so pinning a source for one contract does not move another contract's fingerprints.

Zone-coded hazards

Storm Events codes convective hazards against counties and most broad-scale hazards — heat, tropical cyclones, winter storms, wildfire — against NWS forecast zones. A zone-coded row carries a state and a zone number, not a county, so it cannot join to a county universe on its own. Under drop such rows are discarded, which is exact for county-coded hazards and badly under-counts zone-coded ones; under expand each is mapped to every county in its zone. Either way readiness panel counts exactly what happened — dropped, expanded, or unmappable because the zone is not in the current crosswalk edition — so a thin panel is explained, not mistaken for a rare hazard.

Continuity
Report §7 warns that federal series can stop: NOAA retired its Billion-Dollar Disasters product in May 2025 with no updates beyond CY2024. Hence the pinning, and hence --keep-raw for mirroring what licences allow.

Licences
All three sources are US Government works in the public domain; attribution per DATA-LICENSES.md.

05 · Panel and splits

A dense panel, three locked splits, one training channel.

The panel crosses every region in the scope with every year and period of the contract, then marks the cells that saw a damaging event. Storm Events only records events; the Census county file supplies the zeros. Every unit is labelled 0 or 1, and the panel's digest — over units and labels — identifies an exact dataset.

Which years are training years is set by the contract, never by the harness. TrainingView carries training-year units and their labels (fitting needs them) and refuses to expose anything else; it records a digest of exactly what it exposed, so the canary can later check a model fitted on what it claims. PredictionRequest carries units with no labels at all. The validate split may be scored as often as you like; test may be touched once per model version, ever, and the count lives on disk next to the ledger.

Base rates drift
On the tornado contract the base rate is 5.6% in training, 8.1% in validation and 10.3% in the untouched test years. A model calibrated on 1996–2015 will be under-confident later — visible before any model exists, because the panel is dense and the splits are locked.

06 · The models

Climatology baselines, then real candidates on harness-built features.

Models are hazard- and geography-agnostic by construction: they receive units of the form (region, year, period), and a Phase 1 model additionally receives the harness-built, audited feature rows for those same units — never a panel, never a label. Construction goes through a registry, so neither an agent nor a CLI user imports engine classes directly or passes a panel into a constructor — which is exactly how the leaky oracle cheats, and why building it requires naming it and handing it the panel explicitly.

The baseline queue

The local backend walks the same short baseline queue for every contract by default; --queue phase1 runs it and then the feature candidates (logistic, logistic+iso, gbm, gbm+iso), skipping any that need a source that was not loaded. Each candidate carries the two fields a human writes on an experiment card — what changed and why it should help, stated so it could be wrong.

Phase 1
Built: the harness-owned feature channel and its firewall, the ERA5/Gazetteer/NRI/pinned-CLIMADA connectors, the logistic/gbm candidates with an isotonic calibrator, loop --queue phase1, promote as the one atomic test touch, the backtest report and verify --phase 1. Remaining: the real-data run that spends the touch. Exit: BSS > 0 on untouched test years with reliability within ±5 pts, published with the ledger.

07 · The harness

Score, then judge — mechanically.

metricwhat it iswhy it is there
Brier scoremean squared error between the forecast probability and the 0/1 outcomestrictly proper: an iterating agent cannot improve it by hedging. Never reported alone — raw Brier is not comparable across base rates.
Brier skill score1 − BS / BS_ref, against the pooled training base ratethe number the contract is written in. > 0 beats climatology; 0 is climatology.
Reliability diagramforecast probability on x, observed frequency on y, per binthe contract requires every populated bin (n ≥ 30) within its tolerance of the diagonal. Thinner bins are reported, not judged.
Murphy decompositionBS = reliability − resolution + uncertaintysays whether a failure is miscalibration (recalibrate) or no signal (needs a feature).
Sharpnessstandard deviation of the forecastsa forecast that always issues the base rate is perfectly calibrated and perfectly useless.
AUCprobability a random positive outranks a random negative; ties get half creditso a constant forecast scores exactly 0.5. The contract sets the floor.

The verdict

Five checks, applied in order: skill relative to climatology; calibration in every populated bin; discrimination; provenance — the card must carry the current contract's digest; and the split — a card scored on training years can never pass. A scorecard is never produced without its canary report: every command that scores anything goes through one function, scoring.screen().

Pure standard library
The eval plane is the one component that must produce identical numbers on any machine from a clean clone, so it takes no dependency whose version could move under it. The package has no runtime dependencies at all — which is also why the whole thing runs in your browser.

08 · The leakage canary

A smoke alarm, not a proof.

The primary defence against a model scoring itself on data it should not have is structural — the two invariants above. The canary is the tripwire for when that structure is breached: an accidental join that carries the label column, a feature computed over the full panel, an agent that read a file it should not have. It is five heuristics over a model's output — the fifth, feature provenance, is skipped for a model that declares no features, so a Phase 0 verdict is unchanged — and every one errs toward rejection: on this task, a forecast that separates outcomes almost perfectly is far more likely to be leaking than to be brilliant, whatever the hazard.

The ceilings are harness policy, not contract terms: no contract may raise them. A sufficiently subtle leak that produces merely-excellent rather than impossible scores will pass — documented rather than papered over. Running the canary across base rates from 8% down to 0.66% is what exposed a check that had been implicitly calibrated to one hazard: judged as a pooled rate, near-zero forecasts on a rare hazard "agree" with the outcomes almost always and looked like a leak. The check is now per outcome class.

The target
leaky-oracle is a model constructed with direct access to the outcomes it is scored on. It is registered, flagged, and cannot be built without the panel being handed over explicitly. Phase 0 does not exit until the harness rejects it.

09 · The ledger

Append-only by hash chaining, anchored against truncation.

Every card carries the hash of the card before it, so edits, reorderings and mid-file deletions break the chain and verify() reports where. Chaining alone does not catch truncation — any prefix of a hash chain is perfectly self-consistent, and "run ten experiments, delete the nine that failed" is exactly the attack that matters here. So the head hash and card count are anchored in a committed sidecar file. Forging both is still possible for anyone with repo write access, but it is now two coordinated edits visible in git history rather than one silent head -n 1.

The file is JSONL, so it diffs cleanly in git and can be read without this code. Each line is a sealed card: the experiment id, a timestamp, the model and version, the split, the three fields a human writes — changed, hypothesis, outcome — the scorecard, the verdict, the canary report, the data snapshot, the contract digest, and the two hashes. The ledgers page re-verifies the committed chains in your browser, and lets you break one to see what each attack looks like.

Reading a card
A ledger of only successes is a marketing document. The outcome field records what happened including when the hypothesis was wrong; the agent's card-writing runbook is in skills/experiment-card.md.

10 · Agent plane

Two backends, the same loop, the same harness.

local

Deterministic and uses no LLM: it walks the fixed baseline queue, then the canary candidate, and writes one sealed card per candidate. This is what CI runs and what the Phase 0 reproducibility criterion is checked against.

readiness loop -c tornado-ok --backend local

claude

A Claude Agent SDK orchestrator runs the same loop with three subagents from report §4 — a hazard analyst for the contract's hazard, a calibration critic, a data steward. Tool grants are Read, Grep, Glob, Bash; none has Write or Edit. Needs pip install 'readiness-loop[agent]' and an API key.

readiness loop -c tornado-ok --backend claude

The orchestrator's system prompt names the rules it cannot negotiate: it may propose any model in the engine; it may not modify anything under the harness, the contracts module, the config or the registry; it never sees holdout labels; the validate split is its to iterate against and the test split may be touched once per model version; and every experiment gets a card, including the ones that did not help.

MCP

readiness mcp -c NAME serves the pinned data and the contract's ledger over MCP — stdio, standard-library JSON-RPC, no dependencies. Every tool is a read. get_region_history exposes training years only; there is no tool that returns a holdout outcome, and a test asserts it.

Phase 2
"parallelise with subagents: hurricane wind, wildfire, tornado, heat" is a loop over registered contracts with one hazard analyst each, not a redesign.

12 · Roadmapreport §6

Five phases, each with a falsifiable exit.

Phase 0 — harness before model · complete

The eval plane, pinned data and the experiment ledger, for any hazard. Exit: the climatology baselines reproduce bit-for-bit from a clean clone, and the harness rejects a deliberately leaked model.

Phase 1 — the loop, on one hazard

Real candidate models, ERA5 features, CLIMADA integration. Exit: BSS > 0 on untouched test years with reliability within ±5 pts, published with the ledger.

Phase 2 — multi-hazard, national, with exposure

One registered contract per peril against the same harness; join to USA Structures so outputs become human.

Phase 3 — the planning thought-partner

Scenario stress-tests of a facility's emergency plan against the validated risk layer. Case studies become regression tests. Seeded in plans/.

Phase 4 — global scale-out

Swap US layers for Open Buildings, Flood Hub, EM-DAT. The architecture does not change; the connectors do.

The design the implementation follows is the research briefing; its fifth section is this page in prose.
